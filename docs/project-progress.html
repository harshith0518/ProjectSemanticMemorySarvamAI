02 / THE COMPLETE LEARNING PATH

From your input
to a supported memory.

Saving an observation and learning a memory are separate actions. The model proposes meaning; the backend decides which structurally valid changes may be committed.

Implemented contract path
InputWhat the user supplied
SourceThe preserved original
ProposalA model interpretation
Guarded commitValidated, atomic writes
MemoryClaim + evidence + history
Full map · follow 01 through 12Choose a stage for its explanation below. On small screens, scroll the map sideways.
Transaction boundary: stages 8-10 separate responsibilities visually; final validation, reconciliation writes and publication of the job result happen in the guarded commit path. An earlier validation cannot authorize a later unchecked write. Search indexes also track the source commit at stage 4.
Stage 01 / User action

Give the system an observation.

What happens

Type or paste a note, optionally supply a formatted version, or import a JSONL file. Save a note is explicit durable intent in Normal mode.

Why it matters

An Ask question is a temporary request. Neither that question nor a generated reply silently becomes learning evidence. There is no microphone or ASR integration in this version.

Implementation: Browser input contract

Private stops early

The browser keeps only a temporary scratchpad. Saved API operations reject Private before reading bodies or opening the personal store. No provider request or later backfill.

Failure is not a memory decision

A timeout or invalid proposal is a failure, not no_memory. Failed calls remain accounted for. Retry and schema repair are bounded.

A stale worker cannot publish

If Forget, Correct or a newer lease invalidates the snapshot, commit is refused. A successful job receipt prevents replay from creating duplicate memory.

03 / WHAT IS ACTUALLY STORED

Memory is a claim
with a route back to its source.

PostgreSQL is the canonical store. Text preserves the original; JSONB holds typed meaning; relational links preserve ownership, support and revision history.

Evidence status and lifecycle differ

Reported / tentative / disputed describe the claim's evidence or certainty. Active / superseded / corrected / excluded describe whether and how it can be used.

An active claim can still be tentative. A reported event is not independent verification that an external action occurred.

Installed pgvector is not implemented vector search

pgvector is enabled, but this version stores no embeddings. Search uses two PostgreSQL GIN expression indexes and full-text ranking. Dense retrieval is a deferred experiment.

The index is a rebuildable search aid. Canonical source text and claim revisions remain the evidence.

05 / THE SECOND HALF: MEMORY TO ANSWER

Retrieve evidence.
Then answer within it.

Learning produces inspectable state. Ask is a separate request that uses the current permitted evidence and never silently saves the question or response.

Kimi live baseline incomplete

  1. Current question

    The user selects Ask and a collection. Backend identity and Normal/provider gates apply. Current instructions take priority over remembered style.

  2. Select a representation

    Original-source search is the default. Alternatives are sources plus memories, or all permitted history. The implemented Ask comparison uses a 24,000-byte evidence allowance.

  3. Build an evidence packet

    Filter owners, collection, eligibility, lifecycle and exclusions. Keep paired originals, exact claim support, uncertainty and required correction/change annotations together.

  4. Bounded Kimi request

    Check the exact public synthetic allowlist and reserve usage. Call the responder outside SQL locks. The model produces an answer/draft or an abstention with evidence references.

  5. Recheck before release

    Validate citations against the packet and recheck current evidence/policy under the commit guard. Reject a response made stale by Correct or Forget. Buffer before publication.

  6. Show answer and Sources

    Expose citations and feedback. A draft is not sent. No-evidence, no lexical matches and an operational failure have different meanings; a timeout is not proof that a fact is unknown.

Why source-only stays the default

The final authored diagnostic found all required evidence in 45/45 answerable attempts for both source-only and source-plus-memory. Source-only was faster and selected fewer evidence bytes.

Source-only: 2,368.94 mean bytes, 60.75 ms p50. Sources + memories: 5,492.88 mean bytes, 98.05 ms p50. These are local diagnostic measurements with deterministic claims, not live answer accuracy.

What the retrieval experiment taught us

Initial memory fusion displaced an original note needed to distinguish two people named Ravi. Reserving the strongest source match repaired the diagnostic miss.

The original 42/45 result is retained. RRF combines ranks, not truth probabilities. GIN search uses PostgreSQL full-text ranking, not BM25 or dense embeddings.

Budget precision: 24,000 serialized UTF-8 bytes is not 24,000 tokens and does not guarantee equal token counts across representations. Whole records are preserved; overflow is explicit rather than silently clipping a condition.

06 / MEMORY REMAINS UNDER USER CONTROL

Repair the interpretation.
Respect the user's boundaries.

Controls use explicit intent, impact preview, confirmation and the same backend policy guard as workers and answer publication.

Correct

The interpretation was wrong.

Provide a statement and confirm its typed meaning. Preserve the original source, mark the old interpretation corrected, and attach the amendment to later evidence.

Example: the extracted date was wrong from the start. This is a repair, not a new event in the world.

Record a world change

The world has changed.

Save a supported successor and mark the predecessor superseded. Retain the old state so historical questions can still be answered honestly.

Example: a launch genuinely moved from the 18th to the 21st. Late import time alone cannot establish that change.

Forget

Stop future use and relearning.

Preview the affected support, then exclude the claim family's supporting observations, dependent claims and known exact copies or literal passage reimports across the owner.

Originals remain inspectable. Whole-note exclusion can also make unrelated details unavailable. Novel paraphrases are not automatically detected.

Private

Temporary current context only.

The actual UI is a local scratchpad. It reads no saved personal data, sends no provider requests and creates no durable private content, activity or jobs. Exit clears it; nothing is backfilled.

Changing mode clears browser work and late responses. A previously accepted Normal import/job can still finish; switching Private is not an undo operation.

The interview concurrency example

What if a worker finishes after Forget?

1. Worker readsIts evidence packet captures policy revision 7.
2. User confirms ForgetThe control locks the owner policy, writes exclusions and commits revision 8.
3. Worker returnsIt acquires the same guard and tries to commit using revision 7.
4. Commit is rejectedStale work cannot reintroduce the forgotten support.

Tests cover this ordering and the reverse using separate real PostgreSQL connections and barriers. Retrieval and buffered answers also recheck revocation. Already released bytes cannot be recalled. Revisions 7 and 8 are illustrative.

Feedback: diagnose whether the problem is memory, world change, retrieval, generation, style or an operational failure. Retrieval/generation diagnoses permit one persisted rerun. Feedback does not silently rewrite global preferences or trigger automatic Ultra fallback.

07 / INTERVIEW PRACTICE

Explain the project
without overstating it.

Start with the problem, walk through one observation, then explain the hardest boundary and the evidence you actually have.

A 60-second technical explanation to adapt
“Kivi turns a user's saved dictations into selective, source-supported memory. I preserve the raw and formatted text as one observation, then explicitly queue processing. A bounded model proposes facts, scoped preferences or useful reported events. Backend code checks the structure and exact evidence, reconciles allowed changes, and commits revisions and support atomically in PostgreSQL. The browser lets users inspect sources, search, ask questions and use Correct, Forget and Private. Workers and controls share a policy guard so stale work cannot reintroduce forgotten evidence. The current prototype has 232 passing backend tests and 22 browser journeys. Live quality is still open: extraction has semantic misses and Kimi has not completed the answer baseline. Next are reliable live evaluation, the varied 500-record corpus and the final reproducibility run.”

This is AI-assisted technical preparation. Adapt it to your own understanding and contribution; it is not an independently authored Part One positioning or vision submission.

1. What problem does semantic memory solve here?

Useful information is spread across notes, changes, preferences and reported events. The goal is to reuse supported understanding in a later answer or draft without forcing the user to repeat everything.

The system preserves originals and creates selective interpretations with provenance. It does not simply compress all history into a profile or treat every sentence as a permanent fact.

2. Is this RAG, a vector database, or model training?

The answer path is retrieval-augmented generation: permitted evidence is supplied to a responder. The memory path adds selective extraction, revision history, reconciliation and user controls.

PostgreSQL is the store. Full-text search is implemented; embeddings are deferred. No model weights are trained by this application. The approved NVIDIA synthetic trial accepts its provider terms, so do not claim the provider has a general no-training or no-retention guarantee.

3. Why keep both raw sources and structured claims?

Sources preserve what was actually said, including details the extractor misses. Claims make reusable understanding inspectable, scoped and revision-aware. Their evidence links let a user check the interpretation.

The live failures demonstrate why sources matter: a valid claim lost the blocker requirement and another failed to reconcile the launch date. Original-source search remains useful when memory is incomplete.

4. Why use one PostgreSQL database?

Sources, claims, jobs, exclusions and receipts need consistent ownership and transactional updates. One relational store lets a control and a worker share an atomic policy guard instead of coordinating independent databases.

TEXT, JSONB and foreign keys cover the initial representation; GIN indexes handle lexical search. A separate graph store, vector service or queue has not shown a necessary benefit for this prototype.

5. What does the model decide, and what does code decide?

Nemotron proposes useful claims, support and semantic relationships. Code owns authorization, schema/quote checks, permitted transitions, budgets, exclusion checks and the transaction. The model has no unrestricted SQL or execution authority.

A real source ID and matching quote prove a reference exists. They do not prove semantic entailment. Repeated live evaluation and manual meaning review remain essential.

6. How do you avoid learning from the wrong material?

Only eligible saved user material can support claims. Ask questions and generated replies are not automatically imported. Imported commands are data, not permission to execute them; evaluator questions and labels stay outside the corpus.

Within eligible material, deciding what deserves a memory is a separate quality problem. No-memory can be correct for a transient instruction, but the live review also found useful observations incorrectly omitted.

7. What is the difference between Correct, change and Forget?

Correct repairs a wrong interpretation. World change preserves the old state as superseded history and adds a successor. Forget excludes supporting material from future use and relearning, including known copies.

All three use explicit confirmed input, an impact preview and a guarded commit. Forget retains visible originals and is conservative at whole-observation level; it does not guarantee detection of unseen paraphrases.

8. How are duplicate imports and worker retries safe?

Import identity is owner plus collection namespace and original record ID. Exact retries return the same source/job state; changed data under the same identity rejects the entire batch. Independent observations with identical words stay distinct.

Worker leases fence expired attempts, and committed processing receipts fence replays. Claims, passages, relations, the receipt and job success commit atomically. Model-call accounting is separate and still includes failures.

9. How do you prove Private and Forget under concurrency?

Tests instrument store/SQL/file/log and browser-persistence attempts, and compare durable state. Private gates are enforced before saved access, not just by hiding the UI.

Lifecycle tests use actual PostgreSQL connections and barriers for both race orderings. They pause work, commit a control, then resume the old packet. Publication must obey the latest policy. Already delivered output is outside recall.

10. What has evaluation actually established?

The latest recorded engineering evidence includes 232 backend tests, 22 Chromium journeys plus targeted follow-ups, and complete state preservation across replacement of application/database containers. Browser model outputs use explicit doubles.

The final authored retrieval diagnostic found all required passages in 45/45 answerable attempts for both representations. This is not a blind semantic score. Live extraction had meaning errors; five Kimi attempts completed no answer. No reliable end-to-end live success claim is supported.

11. Why choose a smaller extractor and a separate responder?

The chosen roles are Nemotron Lightning for memory proposals and Kimi K3 for answers. Separating roles makes it possible to compare extraction cost and quality without changing the answer model.

A smaller extractor being cheaper or better is still a hypothesis here. There is no completed small-versus-stronger comparison and no automatic Ultra fallback. Parameter counts alone cannot establish quality.

12. What would you improve next?

First isolate the response-provider failures and repair the observed extraction misses, then rerun a small repeated live gate. Preserve the original failures and current privacy/revocation contracts.

Next build the varied 500-record corpus with separate held-out scenarios, review any required synthetic allowlist/budget expansion, and compare the same responder under fixed evidence limits. Finally rehearse a fresh checkout through reset and record the exact submission commit.

Observation
One eligible input record, containing raw and optional formatted variants.
Passage
An exact piece of an observation that supports an interpretation.
Claim revision
A stored proposition with qualifiers, lifecycle and links to its evidence.
Reconciliation
Deciding how new supported meaning relates to existing claims.
Semantic entailment
Whether the evidence really supports the meaning of the claim, beyond matching a quote.
RRF
Reciprocal-rank fusion: combine ranked lists using rank positions, not confidence or truth scores.
