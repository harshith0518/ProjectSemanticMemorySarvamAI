Kivi is a voice-first interface for computing. T oday, a person can use it in two
ways.
In regular dictation, they speak and Kivi writes. Styles determine how that speech should become
written language, while phonetic memory helps Kivi recognise the words that belong to the
person using it.
In Hey Kivi, the person addresses Kivi directly. This is currently a beta feature. We want Kivi to
understand a request and use tools to help complete it.
Our long-term direction is for Hey Kivi to become the interface through which a person uses the
entire product. Dictation would not disappear; it would become one of the tools available inside
that interface.
Styles and phonetic memory account for almost everything required to make ordinary dictation
personal and correct.
Semantic memory has a different opportunity. It can allow Hey Kivi to understand what has
happened across a person’s work and use that understanding when the person asks for help.
Semantic memory begins where a dictionary ends. It is the durable understanding that allows
a product to recognise the preferences, facts, and context that continue to matter over multiple
interactions.
Your assignment is to decide what semantic memory should mean for Kivi, determine what Hey
Kivi should be able to do with it, and build the product and backend end to end.
There are two parts to this assignment. Complete them in order.
PART ONE
Product Position and Vision
Before designing the interface or choosing an architecture, decide what Kivi should know about
a person—and why.
Use Kivi. Study how other products approach memory, personalisation, context, and user control.
Look beyond feature lists. Consider what kind of relationship each product appears to want with
its user and what that relationship permits it to remember.
Then take a position.
T ell us:
• what semantic memory should allow Kivi to become;
• where the real value is created for the user;
• what deserves to be remembered;
• what Kivi must never assume;
• why someone should trust this system enough to keep using it.
Your position should determine the product you build. It should make some technically

PART TWO
Build and Prove It
Design and build one working end-to-end demonstration of the product you described.
There is no separate prototype. The implemented product is the design.
Its interface, interactions, language, visual character, and backend will be evaluated together.
Begin with the use case
Work backwards from something genuinely useful.
A memory system may be capable of learning ten things while only three of them create
meaningful value for the user. Do not build around everything the system could infer.
Decide which capabilities deserve to exist, then build the product and infrastructure required to
make those capabilities trustworthy.
For example, a person might say:
“Hey Kivi, find the dictation I did around 5 PM yesterday in Slack and
polish it for the meeting I’m walking into.”
Semantic memory may make factual, episodic, and preference-level understanding possible.
Determine which forms of understanding matter for the product you are building, what Hey Kivi
should be able to do with them, and which tools those use cases require.
Build the smallest set of capabilities that produces a product worth using.
Build the complete experience
The end-to-end demonstration should make clear:
• what the person experiences during ordinary use;

• how Kivi’s understanding changes its future behaviour;
• whether that behaviour belongs in regular dictation or Hey Kivi;
• how and when Kivi interfaces with the person when its understanding is incomplete or wrong;
• how the person remains in control without becoming the administrator of the system.
The distinction between regular dictation and Hey Kivi is important. Semantic memory may have
little reason to affect ordinary dictation while being central to an interactive request.
Decide what belongs in each mode and make that boundary coherent in the product.
You have complete freedom over how memory appears within the app. You may create a new
surface, transform an existing part of Kivi, reconsider the navigation, remove current concepts,
introduce new ones, or change the visual identity entirely.
The product should begin and end in an interface intended for a normal user. It should not
require a developer console or an explanation of the underlying system to become intelligible.
You do not need to build speech recognition or integrate with production Kivi. You may replay
transcripts, application context, and other events through a client of your own design.
Build the system beneath it
The visible experience must be connected to a real backend. Its behaviour should come from
actual state, persistence, retrieval, and model decisions—not from a sequence prepared only for
the demonstration.
Choose the architecture yourself. We will not provide Kivi’s memory design, storage model,
retrieval method, prompting strategy, or definition of a memory.
Those decisions should follow from the product position and use cases you established.
Your system should determine:
• what it learns and what it deliberately ignores;
• how a memory is created, represented, stored, changed, and removed;
• how factual, episodic, and preference-level understanding relate to the product you chose to
build;
• how relevant understanding is retrieved when the person uses Hey Kivi;
• how memory influences tool use, responses, or other visible behaviour;
• how an engineer can inspect why memory did or did not affect a result.
Implement only the Hey Kivi tools required by your chosen use cases. A narrow set of tools used
convincingly is more valuable than a broad collection of superficial capabilities.
The system should be narrow enough to finish and complete enough to interrogate. A web or
desktop implementation is acceptable. A notebook, static demonstration, prompt collection, or
architectural proposal is not.

Evaluations
There are two stages to our evaluation.
Y our evaluation
We will first run the evaluation included in your repository.
We will inspect whether it tests the product you actually built, whether the cases are sufficiently
varied, whether failures remain visible, and whether the conclusions follow from the evidence.
Our evaluation
We will then run your complete pipeline on a separate internal corpus of approximately 500
dictations from one user.
Each record will contain:
• raw ASR output;
• LLM-formatted output;
• the ordinary metadata available in our logs.
Your system must provide a documented way for us to import the corpus, process it, inspect the
resulting database and memory state, and operate Hey Kivi against what it has learned.
After ingestion, we will ask Hey Kivi questions grounded in that user’s history.
We will examine:
• which facts, preferences, and episodes Kivi learned;
